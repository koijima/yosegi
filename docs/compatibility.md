# Yosegi Compatibility

Compatibility in Yosegi has multiple layers and should not be inferred only from version numbers.

## Compatibility Layers

```text
File format
  -> Block format
  -> ColumnBinary representation
  -> Binary Maker / Compressor

Java API compatibility is tracked separately.
```

## File Compatibility

A reader must recognize the file header, locate blocks, and resolve the persisted block implementation. Changes to file magic, header structure, block boundaries, or persisted block-reader identifiers can affect compatibility.

## Block Compatibility

A block reader must understand the block's metadata, index, Spread metadata, and column layout. A top-level file may still be recognizable even when its block representation is unsupported.

## Column Binary Compatibility

A reader must have the Binary Maker and Compressor required by each persisted ColumnBinary. Keeping the same logical type is not enough to decode a changed physical representation.

## Persisted Class Names

Some implementation identifiers are stored as Java class names. Such names are part of the persistent compatibility surface when written into files. Renaming or moving these classes can therefore affect old files even if the code change appears to be an internal refactor.

## Encoding Compatibility

A persisted Binary Maker identifier should continue to describe a compatible encoding. If an incompatible encoding is introduced, it should use a distinguishable persistent representation rather than silently changing the meaning of an existing identifier.

## Data Evolution Is Different

Schema-less data evolution and file compatibility are separate concerns.

```text
new field / changing type -> logical data evolution
old writer / new reader   -> persistent compatibility
```

## Compatibility Status

Do not declare writer/reader combinations supported merely because they appear to work. A compatibility guarantee should be backed by automated tests using files produced by the released writer version being claimed as compatible.

Recommended terminology:

| Status | Meaning |
|---|---|
| Supported | Covered by compatibility tests and intended to remain compatible |
| Not supported | Known to be incompatible |
| Not verified | No compatibility guarantee has been established |

## Compatibility Fixtures

Compatibility tests should store files produced by actual released writers, for example:

```text
test/resources/compatibility/
├── version-1.x/
│   ├── primitive.yosegi
│   ├── nested.yosegi
│   ├── array.yosegi
│   └── union.yosegi
└── version-2.x/
    └── ...
```

Fixtures must not be regenerated by the current writer during the test.

## Changes Requiring Compatibility Review

Review compatibility when changing:

- File header or block layout
- ColumnBinary metadata
- Persisted class names
- Binary Makers or Compressors
- Column type identifiers
- Complex child representations
- Block index serialization

See [Testing](testing.md) for recommended verification.
